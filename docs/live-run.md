# Живой прогон

Как поставить задачу на портале и довести её до скачиваемого `.cfe`, `.epf` или `.erf`. Сборка образа и первый подъём контейнера — в [docker.md](docker.md). Разбор сбоев контейнера — в [docker-agent.md](docker-agent.md).

Портал на Ubuntu открывается на порту **18080** (внутри контейнера это 8080). Логин — `WEB_USER`, по умолчанию `admin`. Одновременно выполняется один прогон.

## Перед запуском

1. **Настройки.** `base_url` провайдера, ключ и модель каждой стадии. Аналитик может стоять на другой модели, чем остальные. Таймаут провайдера в профилях — `timeout_ms: 600000` (10 минут): короче этого длинная генерация обрывается на клиенте, хотя провайдер её уже посчитал и выставил счёт.
2. **Эмбеддинги.** Тот же адрес и ключ, модель `text-embedding-3-small`. Без ключа conf-doc хранит только метаданные, а `conf_doc_search` отвечает 500.
3. **Конфигурация.** На странице конфигураций у нужной выгрузки есть каталог и индекс. У conf-doc слот с именем конфигурации (для УТ это `УправлениеТорговлей`) должен быть в статусе `embedding_status: ok`. Проверка без портала: `GET /objects?q=<кусок имени>` на порту 8050 возвращает объекты, `POST /search` с `{"query":"...","top_k":3}` возвращает 200, не 500.
4. **Платформа.** В контейнере есть `/opt/1cv8/x86_64/<версия>/ibcmd` и `1cv8`. Нет обоих — кнопка задачи закрыта. Лицензия должна быть видна процессу в контейнере: без неё `1cv8 DESIGNER` пишет `License not found`.
5. **Веб-поиск** в форме задачи не включать, пока SearXNG не отвечает поиском. Ошибка 415 на этом инструменте уводит агента в обход.

Пока идёт прогон, не перезапускать портал, conf-doc и контейнер. Рестарт портала помечает текущую задачу `interrupted` («процесс портала перезапущен») и сбрасывает очередь в памяти. Пересоздание контейнера затирает правки, которые лежат только в слое контейнера, а не в томе `/data`.

## Как поставить задачу

Форма **Задача** — `/tasks/new`. Следующие задачи встают в очередь.

| Поле | Что ставить |
| --- | --- |
| Конфигурация | Зарегистрированная выгрузка, например `ut11` |
| Заголовок | Короткое имя прогона |
| Бриф | Текст задачи как есть, без подсказки имени объекта метаданных |
| Вид | `cfe` — расширение, `epf` — внешняя обработка, `erf` — внешний отчёт |
| Веб-поиск | Флажок включён по умолчанию. Снять, если SearXNG ещё не отвечает поиском |

Пустой `expect` (`{}`) задачу не останавливает. Аналитик сам фиксирует имена объекта, формы и проверочной процедуры.

Стадии:

- `.cfe`: аналитик → YAxUnit → разработчик → сборщик → сборка `ibcmd`.
- `.epf` и `.erf`: аналитик → разработчик → сборщик. YAxUnit нет.

Флаг «Прогон YAxUnit на платформе» есть только у расширения. Для большой УТ его обычно не включают: тесты пишутся по плану, платформенный прогон YAxUnit не обязателен для сборки файла.

Первая сборка конфигурации загружает XML в `/data/ibs/<config_id>`. Для УТ это долго. Следующие задачи той же конфигурации базу переиспользуют, если штамп `Configuration.xml` совпал с `/data/ibs/<config_id>/cf-stamp.txt`.

## Куда смотреть

Живой лог — `/jobs/<id>`: окно читает `portal.log`, кнопка «Остановить» шлёт сигнал процессу. После конца прогона там же появляются статус, токены и ссылка «Скачать». Карточка задачи — `/runs/<id>`: таблица затрат по стадиям (токены и миллисекунды, без суммы в валюте), `report.json`, ссылки на бинарник, исходники и тесты расширения. Список — `/runs`.

Каталог задачи: `/data/tasks/<id>/`.

| Файл | Зачем |
| --- | --- |
| `status.json` | `queued`, `running`, `passed`, `failed`, `error`, `interrupted`, код выхода |
| `portal.log` | Ход стадий: итерация, токены, инструмент |
| `report.json` | Итог скоринга, если прогон дошёл до конца |
| `cost.json` | Токены и миллисекунды по стадиям |
| `logs/<стадия>/agent.trace.log` | Разрешения инструментов и `directive parse failed` |
| `logs/<стадия>/mcp_usage.jsonl` | Аргументы и ответы MCP |
| `logs/<стадия>/ai_usage.jsonl` | Время завершений модели |
| `artifact/result.cfe` (или `.epf` / `.erf`) | Скачиваемый файл, если сборка его записала |
| `artifact/meta.json` | Имя файла для ссылки «Скачать» |

Домашние каталоги стадий:

`project/.kuibysheff/homes/<id>/{analyst,yaxunit,coder,implementer}/out/`

В логе стадии называются **аналитик**, **yaxunit**, **разработчик**, **сборщик**, затем строка **сборка артефакта**.

### Ретрай сборки XML

Готовый артефакт — успешный load/export через ibcmd/Designer (`artifact/result.cfe` или `.epf`/`.erf`), а не только наличие файлов в `out/`.

При сбое сборки харнес классифицирует ошибку:

| Класс | Пример | Поведение |
| --- | --- | --- |
| `infra` | `failed to prepare infobase`, битый `/data/configs/...` | FAIL сразу, стадии не повторяются |
| `agent_xml` | `sources missing`, `failed to load extension`, `designer failed to build` | ретрай агентов |

Политика при `agent_xml` (флаг `--build-artifact`):

1. До `--build-retries` повторов (по умолчанию **2**, итого до 3 запусков) — только **сборщик** (`implementer`), с `in/build-feedback.md` (хвост `build.log`).
2. Если снова `agent_xml` — один каскад **разработчик → сборщик** с тем же feedback.
3. Логи попыток: `logs/implementer.retry-impl-N.run.json`, `logs/coder.retry-cascade-coder.run.json`.

Ретрай analyst/yaxunit и «починить кэш ИБ» этим циклом не делается.

Ссылка «Скачать» появляется, когда `artifact/result.<вид>` непустой. Статус страницы при этом может остаться `failed`: скоринг и сборка проверяются отдельно.

## Что должно появиться у аналитика

К 8-й итерации в `out/` лежит `agreements.md`. Имена объекта и формы в нём скопированы из `conf_doc_list_objects` / `conf_doc_get_object`, а не придуманы по тексту брифа. Дальше, по одному файлу за ход: `prd.md`, `architecture.md`, `tasks.md`, файл области (`cfe-scope.md`, `epf-scope.md` или `erf-scope.md`), `manifest.json` с `apply_mode` равным `none`.

Нормальный поиск конфигурации:

1. `conf_doc_list_objects` с `q` — подстрока имени.
2. `conf_doc_get_object` с `object_type` и `name`.
3. `conf_doc_search` — если по имени не находится. Индекс для этого уже должен быть `ok`.
4. code-index: только инструменты из `Available MCP tools` этого прогона. Правила вызова — `in/code-index-contract.md`. Инструментов `code-index.search` и `code-index.get_file` нет. `denied` означает, что инструмента нет; тот же вызов не повторять.

После `agreements.md` аналитик больше не листает каталог объектов, а дописывает план. `done=true` в трейсе выглядит как `stop_reason=goal_reached`.

Остановить прогон, не дожидаясь лимита стадии, если к 8-й итерации нет `agreements.md`, либо в `mcp_usage.jsonl` снова `unknown_repo` или HTTP 500. Пустой план всё равно доходит до сборки и падает на пустых исходниках.

## Что смотреть на следующих стадиях

| Стадия | Готовый результат | Плохой знак |
| --- | --- | --- |
| YAxUnit | `out/tests/` или `out/cfe-tests/`, `test-report.md` | нет BSL, `limit_reached` |
| Разработчик | `coder_memory.md` в корне home к 3-й итерации, первый файл `out/src` к 12-й, затем `code-report.md` | пустой `out/src`, `home_write_ok=false`, повтор `in/agreements.md` / `in/tasks.md` после сжатия контекста, вызовы `code-index.search` / `get_file`, `home.run` по дереву конфигурации |
| Сборщик | `out/cfe/Configuration.xml` (для обработки и отчёта — свой корень) | `apply_mode=none` так и остался единственным следом, нет отчёта сборщика |
| Сборка | `artifact/result.cfe` и код 0 у `ibcmd` | `sources missing`, `failed to load extension` |

Разработчик и YAxUnit перед BSL вызывают `sntx_sem` (`get_topic` с полем `topic_id`). У аналитика этого инструмента нет: семантика языка — не его работа.

У разработчика рабочая память — `coder_memory.md` в корне home. Если файла нет, его не читают повторно: один проход по `in/` и запись до 3-й итерации (`Status`, `Contract`, `Facts`, `Next`, `Stopped`, `inputs_read: yes`). Если файл есть, а текста в ходе нет, единственный вызов — `home.read` этого файла, план из `in/` не открывать. В `Facts` лежит последняя находка code-index (`file_path`, `line_start`, `line_end`), в `Next` — не повтор `find_symbol`. Без `inputs_read: yes` code-index не вызывают.

Поиск по конфигурации идёт через `code-index`: состав инструментов — `Available MCP tools` конкретного прогона, не фиксированный список. Правила вызова — `in/code-index-contract.md`. Инструментов `code-index.search` и `code-index.get_file` нет: политика отвечает `denied`. Это не офлайн индекса. `denied` на любом другом имени значит, что инструмента нет; тот же вызов не повторять. `local_tools.read_file` листает файл по символьному `offset`, не по номеру строки.

Остановить стадию разработчика до лимита итераций, если к 12-й нет файла в `out/src`, либо в трейсе уже несколько `policy error: tool code-index.search denied` / `get_file denied` подряд. Типичный провал: `stop_reason=limit_reached`, `home_write_ok=false`, `parse_failures=0` — HTTP к модели был 200, но `home.write` не вызывался ни разу.

Тишина в логе на несколько минут при живом процессе — это ожидание ответа модели в пределах 10 минут, а не зависание. Повтор той же итерации с `directive parse failed` и одинаковым `content_len` — модель зациклилась на неразобранном JSON и до `goal_reached` сама не дойдёт.

## Сбои, которые уже встречались

| Что в логе | Что это значит |
| --- | --- |
| `error sending request` к `chat/completions`, `http_status` пустой | Клиент оборвал запрос раньше, чем модель закончила. Поднять `timeout_ms`. Провайдер при этом может показать запрос как выполненный. |
| `conf_doc_search` HTTP 500, в тексте `OpenAI API key is required` | Процесс conf-doc стартовал до ключа в `/data/conf-doc/config.yaml`. После записи ключа нужен `supervisorctl restart conf-doc`, не портала. |
| `conf_doc_search` HTTP 500, ключ уже есть | Нет векторов. Переиндексация слота. Кэш векторов пишется в конце задания; обрыв посередине результат не сохраняет. |
| `unknown_repo` при `repo=cf` | Алиас индексатора испорчен: аргумент `cf=/data/...` нельзя передавать напрямую в MCP, kbshff дописывает к нему свой каталог. Запуск идёт через `code-index-serve.sh`. |
| `daemon_offline`, `CODE_INDEX_HOME не задана` | В скрипте индексатора нет `CODE_INDEX_HOME=/data/code-index`. Демон при этом может быть запущен. |
| `Путь /data/configs/...\\r не отслеживается` | В скрипт попал CR от `ЗаписьТекста`, и он прилип к пути. Файл скрипта надо переписать без CR. |
| `failed to load extension` и у `1cv8` строка `License not found` | Конфигуратор без лицензии. Ошибку XML при этом показывает `ibcmd`, не дизайнер. |
| `Loading an extension cannot change the belonging of the root configuration object` | В `Configuration.xml` нет выгрузки расширения (`ObjectBelonging`, назначение, состав). Каталог сборщика — черновик, а не исходники CFE. |
| `sources missing` у `СборкаАртефакта.os` | Сборщик не записал `out/cfe` (для обработки и отчёта — `out/epf` или `out/erf`). Класс `agent_xml`: харнес сам повторит implementer (затем каскад coder), см. «Ретрай сборки XML». |
| `build infra:` / `failed to prepare infobase` | Кэш ИБ или выгрузка CF сломаны. Ретрай агентов не поможет — чинить `--ib-cache` / `--cf-dir`. |
| `agent_stop='limit_reached'` или `'error'` | Стадия не закончила контракт. `goal_reached` в скоринге обязателен для каждой прошедшей стадии. Файл артефакта при этом всё равно может лежать в `artifact/`. |
| `home_write_ok=false` и `limit_reached` у разработчика | За лимит итераций не было ни одного `home.write`: пустой `out/src`. Смотреть, не крутит ли модель запрещённые `search` / `get_file` и не перечитывает ли план после сжатия контекста. |
| `policy error: tool code-index.search denied` (или `get_file`) | Такого инструмента у сервера нет. Следующий вызов — инструмент из `Available MCP tools` этого прогона. Повтор deny до конца лимита — стадию лучше остановить. |

Харнес сам поднимает лимиты, если в профиле они ниже: `max_tokens` не меньше 8000000 на каждой стадии, `max_duration_sec` не меньше 24000 (у аналитика не меньше 54000), у аналитика и разработчика `max_iterations` не меньше 100. В форме настроек эти числа не задаются. Таймаут провайдера берётся из профиля (`timeout_ms: 600000` в `agent-config.example.yaml`).
